## 一、需求

### 1.1 本模块要解决的问题

附加模块（Agent / MCP）在铜傀儡生态里此前只有需求文档，没有可 clone 的骨架。结果是每个开发者都要自己摸索 `Module` trait、`registerModule`、i18n 命名空间、DB scope 等约定，而这些约定写错时**不报错，只表现为「运行起来没反应」**。

本仓库是该问题的载体：一个可直接 clone 的模块骨架，同时提供打包、校验与提审链路。

### 1.2 目标用户与诉求

| 用户 | 诉求 |
|---|---|
| 第三方模块开发者 | 不读完整内核源码就能写出可运行、可打包、可被收录的模块 |
| 模组作者（非 Rust 背景） | 只要写 Vue 页面 + 少量 Rust 命令就能接入启动器 |
| 铜傀儡官方维护者 | 收录审核有统一元数据契约，避免每个模块各写一套打包脚本 |
| 终端用户 | 在启动器模块列表里一键下载、安装、启停第三方模块 |

### 1.3 功能需求

| 编号 | 需求 | 落地载体 |
|---|---|---|
| R1 | 契约零猜测：模块清单在编辑器内实时校验 | `module.schema.json` + `scripts/validate-manifest.mjs` |
| R2 | clone 后即可运行，无需改任何配置文件 | `package.json` 脚本 + `vite.config.ts` |
| R3 | 一条命令打包，产出 zip + 校验值，版本取自 `module.json` | `scripts/package-module.mjs` |
| R4 | 一条命令预览提审条目 | `package.json` 的 `submit` 脚本 |
| R5 | 新人 30 分钟内理解「该改哪几个文件」 | `README.md` + `AGENTS.md` + `docs/` 三份文档 |
| R6 | 语言包键集一致性可自动校验 | `scripts/validate-manifest.mjs --check-locales` |
| R7 | 发布结构可被测试断言 | `tests/package-layout.spec.mjs` |
| R8 | 现状诚实：明确区分阶段一与阶段二，不承诺未实现能力 | 本文第一章 1.5、第二章 2.4、第三章 3.1 |

### 1.4 非功能需求

- 文档写在 `/docs`，每份文档含**需求 / 架构 / 备注**三章节（本文即此结构）。
- **文件命名写该文件的作用，不与执行顺序挂钩**（故不出现 `step1_init.rs`、`01_build.yml`）。
- 禁止 emoji，图标一律用 `@lucide/vue` 图标名（如 `Puzzle`）。
- 前端消费 `var(--copper-*)` 主题令牌，接入 i18n，不硬编码文案与颜色。
- 打包脚本零运行时依赖，产物体积与内容可预测、可逐字节复现（CI 与本地得到同一份 sha256）。

### 1.5 成功标准与当前达成度

| 标准 | 量化口径 | 当前状态 |
|---|---|---|
| clone 后即可运行 | `git clone` → `npm install` → `npm run dev` | **前端链路已实测通过**（dev server 与跨仓库 import 解析成功）。后端编译受阻于 G14 / G15，见 2.4 |

## 二、架构

### 2.1 仓库关系

```
cgl-models（本仓库：模板 / 骨架）
   │  提供：骨架 + module.json + 打包 workflow + 提审 bot workflow
   │  产出：模块包 .cglm（manifest / 后端产物 / 前端 dist）+ sha256
   ▼
cgl-libs（官方元数据仓库，收录条目）
   │  收录：模块条目 JSON + 下载地址 + 校验值
   │  门禁：管理员审核 PR 后才进入列表
   ▼
铜傀儡启动器（CopperCore）
      模块列表拉取 cgl-libs -> 用户下载 -> 安装到 paths.modules_dir() -> 装载
```

三者职责：本仓库管**怎么写和怎么打包**，`cgl-libs` 管**收录什么**，`CopperCore` 管**怎么装载与运行**。

### 2.3 关键设计决策

| 决策 | 理由 |
|---|---|
| `module.json` 作为唯一数据源 | 内核读它做装载与展示，CI 读它做打包与提审；两处读同一份，不会漂移 |
| 身份与 i18n 命名空间拆成两个字段（`id` / `i18n_namespace`） | 两段式 `id` 含点号，而 `t()` 按点号拆段；硬塞进一个字段必然冲突。详见 [模块契约](模块契约.md) 第七章 |
| 语言包放前端目录、后端 `include_str!` 同源引入 | 与内置模块同构，实现单一数据源 |
| 打包脚本自研 zip writer（store 模式） | 包内结构是冻结契约，且必须逐文件生成 `manifest.sha256`；依赖外部 zip 工具会让结构随平台漂移 |
| 打包不做 deflate 压缩 | store 让体积与内容完全可预测、可逐字节复现（CI 与本地同 sha256），压缩交给 Release 传输层 |
| `permissions` 默认空数组 | 权限最小化；模板不应携带自己用不到的权限 |
| 前端命令调用统一经 `api/core.ts` 的 `call` | 禁止裸调 `invoke`；错误归一化后才能做可读的失败展示 |
| `api.ts` 把「命令未注册」归一化为可读状态 | 阶段一命令确实进不了内核的静态列表，页面须如实展示「命令不可用」而非假装可用 |

### 2.4 阶段划分（本仓库的核心架构事实）

**阶段一（当前已打通「编译 + 自检」链路，尚未挂进启动器 UI）**：模块以**源码依赖**形态交付——`src-tauri/` 作为 path 依赖接入内核，前端包被内核 `frontend/src/modules/index.ts` 静态 `import`，二者随内核一起编译。

- 本阶段打包产物用于**分发源码包 + 校验值**，供开发者自行编译。
- 属开发期分发，**不进入面向终端用户的一键安装链路**。
- 设计上的目标是链路跑通：编译进内核 → 出现在左导航 → 语言包正确 → 命令可调用。

**阶段一的两处前置阻塞现已解除**（见 3.1 的 G14、G15）：
1. **G14（内核侧）已解除**：内核 `CopperCore/src-tauri/src/lib.rs` 已开放 `pub mod registry / pub mod services / pub mod error / pub mod state`，本仓库 `src-tauri/` 可正常命名 `KernelContext` / `Module` / `KernelError` 等类型。
2. **G15（环境侧）已解除**：内核依赖 `openssl` 的链接问题在本机经 `CopperCore/.cargo/env-check.ps1` 配置 `OPENSSL_DIR` 后解决。

**已实测通过的部分**：前端链路与工具链（`scripts/validate-manifest.mjs`、`node --test`、`vue-tsc`、`vite build`、`npm run dev`、`package-module.mjs`、`validate-release-assets.mjs`、`build-libs-entry.mjs --dry-run`），以及**后端编译与 `cargo test`（35 项全部通过）**。

**阶段一仍未验证的部分**：模块尚未真正装载进启动器 UI（左导航 / 语言包 / 命令调用需等内核侧装配本模板的 `module.rs` 并静态引入其前端入口）。

**阶段二（内核待实现）**：内核支持动态加载后，发布包为二进制形态（manifest + 后端动态库 + 前端 dist），用户一键下载即用。

本模板的**包结构现在就按阶段二的最终形态定义**，避免届时改契约。契约（`module.json` / 包结构 / 提审条目）在阶段一即固定并冻结。

### 2.5 与其它模块的关系

| 关联方 | 关系 |
|---|---|
| `CopperCore`（铜内核） | 契约的唯一来源。本仓库的 `Module` trait 实现、`KernelContext` 用法、事件 / 意图 / i18n / DB 约定全部对齐内核源码 |
| `cgl-libs`（元数据仓库） | 下游。本仓库的 Release 产出经提审 bot 变成 `cgl-libs` 的条目；字段映射方向固定为 manifest → 条目 |

| 其它附加模块 | **不互相依赖**。模块间只经事件总线与意图注册表中转 |

## 三、备注

### 3.1 现状差距（诚实标注）

以下均为当前**内核侧的真实状态**。本仓库的文档必须与之一致，禁止把未实现写成已实现。编号沿用主仓库 `docs/cgl-models.md` 3.4 的缺口表。

| 编号 | 缺口 | 对本模板的影响 |
|---|---|---|
| G1 | **附加模块动态加载未实现** | 阶段一只能走静态编译路径；本仓库的分发形态区分必须保留 |
| G2 | `ModuleRegistry` 无磁盘装载路径（只有 `register` / `register_with_origin` + `boot()`） | 阶段二必须新增装载器；`module.json` 的 `backend.entry` / `artifact_glob` 是为此预留 |
| G3 | ~~`is_builtin` 恒为 `true`~~ **已修复** | 内核新增 `ModuleOrigin`（`Builtin` / `Addon`）与 `register_with_origin`，设置页已能区分内置 / 附加模块 |
| G4 | 前端 `registerModule` 非公开接口 | 附加模块前端无法在运行期注册；本仓库 `register.ts` 目前经相对路径被内核静态引入 |
| G5 | 前端语言包为静态映射（`MODULE_LOCALES` 硬编码内置三模块） | 附加模块语言包当前无法进入前端本地兜底；阶段二需改为运行期注册 |
| G6 | 命令注册为静态列表（`generate_handler![...]` 硬编码） | 附加模块命令无法注册；本仓库 `api.ts` 把该失败归一化为 `not_registered` |
| G7 | 手动导入命令不存在（沙箱命令已有，导入命令未实现） | `npm run import:dev` 只能直接写文件系统 |
| G8 | 目录已预留但未使用（`services/paths.rs` 已定义 `modules_dir()`） | 目录约定可直接落地，风险低 |
| G9 | `cgl-libs` 条目契约已收敛，但仓库实体与 CI 尚未创建 | 端到端提审链路无法在当前工作区验证 |
| G10 | 模块签名与来源校验未实现 | 「未收录 / 未审核」标识只能靠 UI 明示，无法由签名支撑 |
| G11 | `debug_log` 命令与模块日志无约定 | 按模块 id 分文件的日志约定待定义 |
| G12 | **沙箱判定已落地，子进程托管与 IPC 未落地** | 9 项内核权限枚举、授权上界、路径穿越拦截、越权留痕与超限强制停用已可用；但「附加模块跑在独立进程」这一物理隔离尚未生效 |

### 3.2 风险点

| 风险 | 说明 | 缓解 |
|---|---|---|
| 阶段一尚未真正挂进启动器 UI | G14（模块可见性）与本机 OpenSSL 虽已解决、编译与自检通过，但 `DemoModule` 尚未被内核 `lib.rs` 装配、前端入口也未被静态引入 | 本文 2.4 明示"已打通编译+自检，未挂 UI"；[开发指南](开发指南.md) 有排查表 |
| 阶段一的手工接入步骤容易被忽略 | 模块的命令必须进内核的静态列表、前端必须进 `modules/index.ts` 的 import，否则「没反应」 | 本文 2.4 明示；[开发指南](开发指南.md) 有排查表 |
| i18n 命名空间前后端不一致 | 表现是文案整体回退键名，不报错。项目历史上已踩过同类 bug | [模块契约](模块契约.md) 第七章单列；CI 校验命名空间唯一性 |
| 契约在阶段二被改动 | 若内核实现动态加载时改契约，已收录模块会批量失效 | 三份契约（manifest / 包结构 / 条目 JSON）阶段一即冻结；改契约须同步升 `api_version` / `schema_version` |
| 提审链路无法端到端验证 | `cgl-libs` 仓库实体与 CI 尚未创建 | 本地 `npm run submit --dry-run` 预览条目；链路按 `cgl-libs` 契约实现 |
| 打包产物可复现性 | 若引入压缩或非确定性的时间戳，CI 与本地 sha256 会不一致 | zip writer 使用 store 模式 + 固定时间戳常量 |
| 权限声明与行为不一致 | 收录审核红线第 7 条；不一致即拒绝合并 | `permissions` 默认空；每增一项须在 README 写清申请理由 |
